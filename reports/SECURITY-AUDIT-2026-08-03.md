## Коротко — для тих, хто не читатиме все

**CPP-DOSE технічно не може «злити» дані користувача, тому що в застосунку
немає жодного шляху кудись їх надіслати.** Не «обіцяно не надсилати» — а
відсутній сам код, що вмів би це робити, і це перевірено чотирма незалежними
способами (нижче, розділ 1), включно з автоматичним тестом, який зараз
проходить.

Практично для людини, яка встановлює застосунок або додає його на робочий
екран, це означає:

- **Немає акаунта.** Нема реєстрації, нема логіна, нема пароля що можна
  вкрасти.
- **Немає інтернету в роботі.** Застосунок повністю функціональний в режимі
  польоту. Жодного разу, ні для чого.
- **Немає збору даних.** Нема аналітики, нема телеметрії, нема відправки
  «статистики використання» кудись.
- **Не питає зайвих дозволів.** На Android — лише дозвіл на будильники/сповіщення
  (щоб сигнал крапельниці спрацював і при заблокованому екрані) і той, що
  вимагає сама системна WebView-компонента (не використовується для передачі
  даних — див. розділ 3). Ані камери, ані контактів, ані геолокації, ані
  доступу до фото ще ніхто не запитував.
- **Ім'я/позначку пацієнта, яку медик вводить у полі нотатки, застосунок
  свідомо ніколи не зберігає на диск і ніколи не показує в сповіщенні** — це
  окреме, задокументоване інженерне рішення в коді (розділ 2), не обіцянка «в
  майбутньому зробимо».

Для фондів: нижче — не маркетингове запевнення, а перелік конкретних
перевірених фактів з кодом і командами, якими ви (чи ваш технічний консультант)
можете відтворити кожен висновок самостійно за 10 хвилин.

## 1. Мережа та витік даних — перевірено 5 незалежними способами

Constitution Art. V вимагає нуль мережевих викликів під час роботи. Це не лише
задекларовано — воно enforced на п'яти різних рівнях, кожен з яких ловить
регресію незалежно від інших:

1. **Content-Security-Policy** (`index.html`) — `connect-src 'self'` заборонює
   будь-який вихідний запит (`fetch`/XHR/WebSocket/beacon) на чужий origin на
   рівні браузера/WebView, ще до того, як спрацював би будь-який JS-код:
   ```
   default-src 'self'; connect-src 'self'; img-src 'self' data:;
   style-src 'self' 'unsafe-inline'; script-src 'self'; object-src 'none';
   base-uri 'self'; form-action 'none'
   ```
2. **ESLint-правила** (`eslint.config.js`) забороняють навіть *посилатися* на
   `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `navigator.sendBeacon`
   у вихідному коді — `npm run lint` падає на компіляції, не в рантаймі.
   Підтверджено: `npm run lint` пройшов чисто на поточному коміті.
3. **Автоматичний тест** (`tests/offline.test.tsx`) підміняє `fetch`,
   `XMLHttpRequest`, `WebSocket`, `EventSource`, `navigator.sendBeacon` на
   шпигуни, які кидають виняток при виклику, рендерить весь застосунок і
   проходить по кожному екрану (Крапельниця, Препарати, Про застосунок,
   Застереження) — і перевіряє, що жоден шпигун не спрацював. **Пройдено
   зараз**, під час цього аудиту.
4. **Прямий пошук по коду**: жодного виклику `fetch(`, `XMLHttpRequest`,
   `axios`, `sendBeacon`, `WebSocket` в `src/` поза тестовими моками не
   знайдено.
5. **Зібраний service worker** (`dist/sw.js`) — перевірений безпосередньо:
   precache-список містить лише статичні файли застосунку (HTML/CSS/JS/іконки/
   маніфест), `runtimeCaching: []` у конфігурації (`vite.config.ts`), тобто
   service worker не робить жодного мережевого запиту під час роботи — лише
   віддає раз завантажені локальні файли.

Додатково: `capacitor.config.ts` не містить `server`-блоку — нативна WebView
завантажує **тільки** зібраний офлайн-бандл, без live-reload сервера й без
жодного мережевого origin, куди вона могла б звернутись.

Жодних акаунтів, аналітики, телеметрії чи SDK для збору статистики в коді чи
залежностях немає.

## 2. Зберігання даних на пристрої

Застосунок використовує лише `localStorage` (жодного IndexedDB/cookies/
зовнішньої БД). Повний перелік ключів, знайдених у коді:

| Ключ | Що зберігає | Чутливість |
|---|---|---|
| `disclaimer-ack` (App.tsx) | Прапорець «застереження прочитано» | Немає |
| тема (ThemeToggle) | light/dark | Немає |
| `cpp-dose.liveDrips.v1` | Активні крапельниці: числа (швидкість, обʼєм), мітки часу, ідентифікатор клінічного запису | Оперативні дані, без ПІБ |

Для крапельниць зберігання спроєктовано як **явний білий список полів**
(`src/drip/persistence.ts`), а не серіалізація всього обʼєкта — навмисно, щоб
додавання нового поля в майбутньому не почало мовчки писати його на диск.
Явно виключені з диску:

- `displayTag` — вільне текстове поле, куди медик може вписати позивний чи
  бирку ліжка. Може містити щось ідентифікувальне → **ніколи не пишеться в
  `localStorage` і ніколи не потрапляє в текст сповіщення** (див. розділ 3 про
  видимість сповіщень на заблокованому екрані). Живе лише в оперативній
  пам'яті вкладки й зникає при закритті застосунку чи видаленні крапельниці.
- Знімок самого клінічного запису (назва/доза/джерело) — при відновленні після
  перезапуску переresolve-иться заново з перевіреного бандла за ID, а не
  дублюється в змінюваному сховищі (щоб не з'явилась друга, неперевірена копія
  клінічного значення — Art. I/II Конституції).

Дані, що читаються назад зі сховища, проходять повну валідацію перед
використанням (`deserializeDrips`): відхиляється все, що не є коректним
масивом, що має неправильний тип поля, що виходить за санітарні межі (наприклад
`dropFactor` поза діапазоном, `gtt`/`mlPerH` ≤ 0, час старту в майбутньому) —
пошкоджений або підроблений запис у сховищі просто відкидається, а не
призводить до показу оманливих чисел. Це підтверджено 16 окремими тестами
(`tests/drip-persistence.test.ts`), усі проходять.

**Висновок:** на диску пристрою немає нічого, що ідентифікує пацієнта. Немає
навіть теоретичного шляху, яким текст із поля позивного/бирки міг би туди
потрапити — це не політика, а структурна властивість коду (типобезпечний
явний білий список полів у `serializeDrips`).

## 3. Дозволи на платформі (Android / iOS)

**Android** (`AndroidManifest.xml`, повний перелік дозволів застосунку):

| Дозвіл | Навіщо | Чи стосується мережі/даних |
|---|---|---|
| `INTERNET` | Вимагається самим Android для WebView-компонента навіть якщо вона завантажує лише локальні файли — платформна вимога Capacitor/Android, не вибір застосунку | Ні — фактичне використання мережі виключено розділом 1 |
| `USE_EXACT_ALARM` | Щоб сигнал «мішок скоро закінчиться» спрацював точно, навіть при заблокованому екрані (FR-12) — не потрапляє під Play-обмеження, бо застосунок не поширюється через Play Store як direct-APK збірка | Ні |
| `POST_NOTIFICATIONS`, `VIBRATE`, `RECEIVE_BOOT_COMPLETED`, `WAKE_LOCK` | Автоматично додаються плагіном `@capacitor/local-notifications` для локальних (не мережевих) сповіщень-будильників | Ні |

Немає дозволів на камеру, геолокацію, контакти, мікрофон, SMS, зовнішнє
сховище/фото, Bluetooth. `MainActivity.java` — рядок коду, стандартний
`BridgeActivity` без кастомних JS-мостів чи увімкненого debug-режиму WebView.

**iOS** (`Info.plist`) — жодного ключа `NSCameraUsageDescription`,
`NSLocationWhenInUseUsageDescription` чи подібного немає, бо жодна така
можливість не запитується. `NSAppTransportSecurity` не перевизначено — діє
дефолтна політика Apple (блокує будь-який нешифрований HTTP), що є моментом
без практичного значення, оскільки застосунок і так не робить мережевих
запитів.

Єдиний застосований сторонній патч (`patches/@capacitor+local-notifications+…`)
— одна змінена константа в Android-плагіні: видимість сповіщення з `PRIVATE`
на `PUBLIC`, щоб текст сигналу крапельниці (назва препарату, темп) був видний
і на заблокованому екрані — свідоме рішення Власника (задокументоване в
`decisions/ADR-0008-notification-saga.md`), продиктоване тим, що медик під
навантаженням не завжди розблоковує телефон, щоб побачити сигнал. Саме тому
розділ 2 підкреслює, що *ідентифікувальний* текст (позивний/бирка) з цього
сповіщення структурно виключений — залишається лише клінічно-нейтральна
інформація («крапельниця, 30 крап/хв»), без прив'язки до конкретної людини.

## 4. Безпека клієнтського коду

Повний пошук по `src/` не знайшов жодного використання `eval()`,
`dangerouslySetInnerHTML`, прямого присвоєння `innerHTML`, `document.write` —
класичних джерел XSS. Увесь UI — звичайний React JSX з даними з локального,
статично зібраного бандла (`clinical/field-bundle.json`), не з довільного
зовнішнього вводу, який міг би нести розмітку.

## 5. Ланцюг постачання / залежності

Продакшн-залежностей — **чотири**: `@capacitor/core`, `@capacitor/haptics`,
`@capacitor/local-notifications`, `react`, `react-dom` (по суті — Capacitor-ядро
й React). Мінімальна поверхня атаки порівняно з типовим фронтенд-проєктом.

- `npm audit --omit=dev` → **0 вразливостей** у продакшн-залежностях.
- Повний `npm audit` (з dev-залежностями) знаходить 11 вразливостей (у т.ч.
  критичні/високі) у пакеті `node-tar`, який тягне за собою `@capacitor/cli` —
  **інструмент розробника для збірки APK, який ніколи не потрапляє в
  застосунок, що встановлює медик.** Це ризик для машини розробника під час
  `npm install`/збірки, не для кінцевого користувача. Рекомендація в розділі
  «Рекомендації» нижче.
- Немає жодного хардкодженого секрету, ключа API, токена чи пароля в коді
  (перевірено пошуком за типовими патернами).
- `android/` та `ios/` — згенеровані Capacitor-ом нативні проєкти, навмисно
  виключені з git (`.gitignore`) і перегенеровуються з веб-збірки — немає
  ризику розбіжності між тим, що в репозиторії, і тим, що фактично зібрано.

## 6. Цілісність збірки й випуску (fail-closed як частина моделі безпеки)

Для інструменту дозування «безпека» — це не лише «дані не витікають», а й «на
екрані ніколи не з'явиться вигадане чи неперевірене число». Це enforced як
release-гейт, і на момент аудиту **живий прогін показав його в дії**:

```
$ npm run validate
✓ validate OK — 39 drugs, 12 prophylaxis regimens, 3 formulas, 6 sources.

$ npm run compile:field
✓ compile:field → included: 31 drugs, 12 prophylaxis, 3 formulas (of which 44 clinical).
  excluded: 8 record(s) (not VERIFIED / not archived).

$ npm run gate:release
✓ gate:release PASSED — no unverified/un-archived record and no TODO() is exposed.
  bundle exposes 44 clinical record(s) + 2 engineering formula(s).

$ npm test
 Test Files  13 passed (13)
      Tests  90 passed (90)

$ npm run lint
(без помилок)
```

`gate:release` провалює збірку, якщо хоч один клінічний запис у зібраному
бандлі не має статусу `VERIFIED:<ім'я>:<дата>` або якщо в бандлі лишився хоч
один літерал `TODO(`. Прямо зараз бандл виключає 8 ще неперевірених записів —
тобто механізм не теоретичний, він активно щось відфільтровує в поточному
стані даних. `src/clinical/guard.ts` (`assertRenderable`) додатково кидає
виняток у рантаймі, якщо хтось спробує відрендерити неперевірений запис — це
дублювальний, а не єдиний захист.

## Залишкові ризики та обмеження

Чесний звіт не буває без цього розділу — нижче те, що аудит **не** закриває
або закриває частково:

1. **Це не незалежна сертифікація.** Формальний зовнішній пентест/аудит (ISO
   27001, OWASP ASVS сторонньою фірмою) — окрема дія, якщо умови гранту фонду
   цього вимагають.
2. **Фізична безпека пристрою поза контролем застосунку.** Якщо телефон
   загублено чи вкрадено розблокованим, локально збережений стан крапельниці
   (числа, час) читається так само, як дані будь-якого іншого застосунку —
   стандартний захист (блокування екрана/PIN) лишається відповідальністю
   користувача, не застосунку.
3. **Текст сповіщення видно на заблокованому екрані** (розділ 3) — свідомий
   компроміс безпеки-в-полі проти конфіденційності: назва препарату й темп
   видно без розблокування, позивний/бирка — ні. Вартий явного підтвердження
   з боку фонду/замовника, що цей компроміс прийнятний для контексту
   розгортання (він уже задокументований як рішення Власника в ADR-0008, але
   фонд, що фінансує розгортання, може захотіти підтвердити його окремо).
4. **Вразливості в dev-залежностях** (`tar` через `@capacitor/cli`) не
   зачіпають кінцевий застосунок, але варті оновлення в рамках гігієни
   інструментарію розробки (нижче).
5. **Разовий знімок у часі.** Звіт відповідає стану коду на коміті `7d7fa12`.
   Кожна наступна зміна коду чи залежностей потребує повторної перевірки —
   рекомендація нижче пропонує зробити частину цього автоматичною.
6. **Один розробник/Owner.** Модель верифікації клінічних даних навмисно
   вимагає єдиного підпису Owner-а (Constitution Art. II) — це сильна
   гарантія цілісності даних, але означає, що доступність оновлень залежить
   від однієї людини. Це організаційне, не кібербезпекове зауваження — просто
   для повноти картини перед фондом.

   в залежностях ловилась автоматично, а не лише під час разових аудитів.
3. **Для довіри кінцевого користувача «на льоту»:** розглянути короткий,
   написаний простою мовою абзац на екрані «Про застосунок» на кшталт

## Як самостійно перевірити кожне твердження (для технічного консультанта фонду)

```bash
npm ci
npm run lint            # немає мережевих API навіть у коді (не лише в рантаймі)
npm test                # 90 тестів, включно з tests/offline.test.tsx
npm run validate         # схема клінічних даних
npm run compile:field && npm run gate:release   # жоден неперевірений запис не потрапляє у збірку
npm audit --omit=dev     # 0 вразливостей у тому, що реально йде в застосунок
grep -R "fetch(\|XMLHttpRequest\|sendBeacon" src/   # порожньо поза тестовими моками
cat index.html           # CSP: connect-src 'self'
cat capacitor.config.ts  # немає server-блоку
```

Кожна команда відтворює один із фактів цього звіту без потреби вірити авдитору
на слово.
