# UI/UX Review — 4 Parallel Expert Passes — Report

- **Date:** 2026-07-22
- **Scope:** full UI surface — `src/App.tsx`, `Navigation`, `FirstRunDisclaimer`,
  `DisclaimerBanner`, `ThemeToggle`, `SourceBadge`, `AboutScreen`, `DrugsScreen`,
  `DripScreen.tsx` (1008 lines), `theme.css` (663 lines).
- **Method:** 4 independent read-only agent reviews, each a distinct lens (field
  ergonomics/accessibility, clinical-safety information design, visual design/
  consistency, information architecture/learnability). No files were touched —
  confirmed via `git status` (only the pre-existing untracked `shot.mjs` scratch
  file, unrelated to this review, remains).
- **Limitation:** no rendered screenshots. Headless Chromium could not launch in
  this sandbox (missing system libraries, no root access to install them), so
  every finding below comes from reading component structure, conditional
  rendering, and the actual CSS rules — not from looking at the app. Anything
  that genuinely needs eyes-on-device is flagged as such inline.

## Cross-cutting findings (flagged independently by 2+ reviewers)

**1. The 10-min / 5-min / empty alarm escalation is audio/haptic-only — nothing
on screen changes.** All four reviewers hit some version of this. `warned10`,
`warned5`, `warnedEmpty` (`DripScreen.tsx` `ActiveDrip`) drive `alarm()`'s beep
count and haptic call but are never read in JSX — confirmed by grep. A card
whose bag is about to run dry looks identical to one with hours left. If a beep
is missed (muted, noisy environment, hearing protection), there's no glanceable
way to recover "how urgent is this drip" from the screen. `--danger` exists in
`theme.css` and is currently used nowhere except the drip-remove confirm button.
*Suggested fix:* border/background color step (`--warn` → `--danger`) and bolded
remaining-time text keyed to `warned10`/`warned5`/`warnedEmpty`, so urgency is
recoverable by sight at any moment, not just audible at one instant.

**2. "Без будильника" (mute) is the least visually prominent control on the
card, despite silencing the app's only safety alarm.** Three reviewers
independently flagged this from different angles: it's the smallest tap target
in the app (20×20px checkbox, no `min-height` on the row — undershoots the
file's own documented "≥48px" rule), it's styled in the same dim gray whether
checked or not, it sits last on the card with no indicator in the collapsed
mini-header, and its scope (per-drip, not global) is conveyed only by code
comments, never by the label text a user actually reads.
*Suggested fix:* bump the tap target to ≥48px; make the *checked* state the
visually loud one (e.g. a `drip-card.silenced` accent + a persistent icon in
the mini-header, not just a dim checkbox); add "(лише цей дріп)" to the label.

**3. Verification provenance doesn't travel with a drip once it's running.**
Both the clinical-safety and field-ergonomics reviews converged on this from
different directions: `SourceBadge` is shown at setup time (tied to the
dropdown selection) but `ActiveDrip` never snapshots which source record it
came from, so neither the running drip card nor the full-screen Focus overlay
— the view a medic actually stares at for hours — shows `source_version`/
`review_status` for the number they're dosing to. Currently low-risk only
because `compile:field` guarantees nothing unverified ships at all; the UI
itself provides no independent visual reinforcement of that guarantee.
*Suggested fix:* snapshot the source id/version/status into `ActiveDrip` at
`addDrip()` time; render a compact badge on the card and Focus overlay for the
drip's whole lifetime.

**4. Same-category concurrent drips are visually indistinguishable.** With up
to 5 concurrent drips, cards can share an identical fallback label ("Дріп" /
"Крапельниця" / "Опікова рідина") with only the live numeric rate to tell them
apart — a real "acted on the wrong bag" risk in a fast multi-casualty scene.
*Suggested fix (cheap, no new input):* auto-append an ordinal when duplicate
labels exist ("Крапельниця 1" / "Крапельниця 2"). A free-text patient tag was
deliberately *not* recommended given the no-patient-data posture of a field
tool that could be captured — flagged as an open question instead.

## Per-lens highlights

### Field ergonomics & accessibility
- Strong existing patterns: stepper-only input (no keyboard), a genuinely
  field-tuned Focus mode (84px digits, 64px buttons, tap-anywhere-to-exit),
  two-tap confirm-to-remove, escalating beep-count alarms, live (not one-shot)
  notification-health banner, wake-lock while any drip runs.
- **New, sharpest finding:** there is no `ErrorBoundary` anywhere in `src/`.
  `assertRenderable()` throws synchronously on any non-VERIFIED record inside a
  render-time `useMemo` — an uncaught throw there unmounts the *entire* app,
  not just the one bad card, which contradicts the constitution's "show
  nothing, with a reason — just for that item" fail-closed intent. This is the
  single largest gap between the constitution's wording and what the code does
  under fault.
- The dedicated night-vision red theme named in `specs/000-product-overview`
  and `plan/architecture.md` was replaced by a generic dark theme (bright blue
  accent) per an informal code-comment "Owner request 2026-07-13," with the
  red mode pushed to `IDEAS.md` — spec text and shipped code now disagree.
  Worth either updating the spec or reprioritizing the red toggle.
- Steppers have no long-press/accelerating repeat; some ranges (dose
  0.1–2mg/kg/h step 0.05) take dozens of taps to move meaningfully.
- A calculable light-theme contrast failure on the bottom nav (`.nav`
  background is hardcoded near-black regardless of theme; inactive-tab text
  resolves to ≈2.5:1 against it in light mode — fails WCAG).

### Clinical-safety information design
- Strong existing patterns: fail-closed is enforced at the *data* layer
  (`compile:field` structurally excludes non-VERIFIED records, not just an
  `if` in JSX) so a raw `TODO(clinical-review)` string can never leak into the
  field UI; blocked states are worded as intentional policy ("відмова у разі
  сумніву") rather than looking like a bug; terminology for "verified" is
  consistent everywhere it appears.
- Engineering-exempt formulas (`drip_rate`, `dose_rate_to_gtt`, both
  `UNVERIFIED` by design/exemption) render in the *same green* as an
  Owner-signed `VERIFIED` record in `SourceBadge` — color, the fastest-scanned
  channel under stress, currently conflates "Owner attested this dose" with
  "this is exempt arithmetic."
- Only one alert-severity tier exists in CSS for at least three real
  severities — the "the alarm itself may not fire on a locked screen" banner
  (arguably the most safety-critical message in the app) is styled identically
  to a routine sedation caution.
- One unstyled fallback (`DrugsScreen`'s "pending" list item has no CSS rule
  at all) sits inside an otherwise-styled reference list, reading as equal
  weight to a fully-dosed sibling entry.

### Visual design & consistency
- Strong existing patterns: a genuinely disciplined color-token system (only
  2 hex-literal outliers in the whole file, both defensible), a real reused
  button-state system, a tokenized radius scale, consistent tabular-nums on
  every numeric readout.
- No equivalent type scale: 18 distinct hardcoded `font-size` values including
  four near-duplicates (11.5/12/12.5/13px) that read as accumulated hand-tuning
  rather than an intentional scale.
- Four structurally different implementations of the same "banner" concept
  (`.caution`/`.notif-warning`, `.notif-hint`, `.bolus`, `.disclaimer-banner`) —
  near-identical box geometry, each reinventing color/font-size independently.
- Two controls undershoot the file's own documented 48px touch-target minimum
  (`.theme-toggle`, `.seg button`, both at 44px).
- `DrugsScreen`/`AboutScreen` use bare semantic HTML with no card/border
  language at all, while `DripScreen` is a fully custom control surface — for
  a safety-critical drug reference list, the lack of per-entry visual grouping
  is a usability gap, not just a style mismatch.
- Dead CSS confirmed via grep (`.drip-label`, `.drip-row`, `.drip-gtt` — zero
  references in the current card markup, leftover from a prior card layout).
- **Assessment: both files show real, traceable signs of incremental-patch
  drift** (dead rules, near-duplicate banners, un-tokenized font sizes, inline
  styles that almost-but-not-quite duplicate an existing class) — worth a
  focused consolidation pass before the next alert/banner type is added,
  though nothing here is currently broken.

### Information architecture & learnability
- Strong existing patterns: nav labels match screen `h1`s exactly; progressive
  disclosure is consistently and correctly state-gated everywhere it's used
  (sedation caution, burn-gated message, bolus hint, calibration button, the
  audio/haptic/flash toggles only appearing while a metronome actually runs);
  warning-severity styling correctly maps to urgency where it exists; the
  per-card "tap for full screen" hint is good always-on in-context guidance.
- **The actual drug name is never shown** — presets are labeled only
  `${use} · ${concentration}` (e.g. "Знеболення · 1 мг/мл"); the real drug name
  never appears in the selector or on the running-drip card. A medic must infer
  the drug from a concentration number alone.
- `DripScreen`'s full setup panel (mode selector, steppers, hero, add button)
  always renders above the active-drips list regardless of how many drips are
  running — once 3-5 drips plus banners exist, checking on an already-running
  drip means scrolling past the whole calculator every time. (Recommended fix
  is reordering/collapsing within the existing screen, not a new tab — the
  flat 3-tab nav itself is the right call and shouldn't grow a 4th item.)
- Terminology collision: the dose-mode segmented-control option is labeled
  "Препарат," the same root word as the Drugs tab's nav label "Препарати" —
  plus three different fallback names ("Дріп"/"Крапельниця"/"Опікова рідина")
  for what's conceptually the same "add a drip" action across modes.
- The bottom nav renders a 4th button (reopen disclaimer) with identical idle
  styling to the 3 real tabs, giving no visual cue it behaves differently
  (opens a modal, doesn't switch screens) until tapped. A clearer,
  action-oriented string (`disclaimer.reopen`, "Показати повне застереження")
  already exists in `uk.json` but is unused — the nav currently references the
  plainer `nav.disclaimer` ("Застереження") instead.

## Open questions for the Owner

1. Was the 2026-07-13 switch from the red-on-black night theme to a generic
   dark theme validated against actual NVG/scotopic-vision use, or should the
   red mode be pulled forward from `IDEAS.md` given the spec still names it as
   a field requirement?
2. Should muting a drip's alarm carry more friction or a stronger persistent
   indicator than today's single, silent checkbox tap — mirroring the
   deliberate friction already given to removing a drip?
3. Is the missing `ErrorBoundary` around clinical-record rendering an accepted
   risk (trusting `compile:field` to make the throw path unreachable in
   practice), or should card-level containment be added so a single bad record
   degrades gracefully instead of blanking the whole app, including other
   active drips?
4. Should engineering-exempt formulas (`drip_rate`, `dose_rate_to_gtt`) keep
   sharing the same green "verified" badge color as Owner-signed clinical
   records, or get a visually distinct tag color?
5. For distinguishing same-category concurrent drips (cross-cutting #4 above):
   is any patient-linked identifier in scope at all for this tool, or does the
   no-patient-data-on-a-capturable-device posture rule that out in favor of
   non-identifying markers only (auto-numbering, "А"/"Б")?
6. Is omitting the literal drug name from presets/active-drip labels
   (info-architecture finding) a deliberate simplification for today's small
   VERIFIED drug set, or an oversight worth fixing now?

## Note on confidence

Everything above is traceable to specific files/lines the four reviewers
actually read (grep-confirmed where relevant — dead CSS, unused i18n strings,
absent `ErrorBoundary`, etc.). Anything that depends on how something actually
*looks* rendered (e.g. whether the "Додати дріп" button sits below the fold,
exact perceived contrast) is called out as needing on-device confirmation
rather than asserted as fact.

No code was changed as part of this review.
